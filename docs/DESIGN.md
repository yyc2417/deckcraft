# 产品取舍

这份文档记录"为什么是这样"，以及被砍掉的东西。功能和代码在 README，这里只写判断。

## 1. 目标用户：一次 10 分钟的汇报

不做"通用 AI PPT"。通用意味着和 Gamma、Kimi、讯飞正面撞，而它们的优势是模板库和素材库——这两样我既做不过，也不该做。

选「一周内要做一次 10 分钟汇报的人」（研究生组会、周报、方案评审），是因为这个场景同时满足三个条件：

1. **材料是现成的文字**。周报、纪要、摘要本来就在手里，AI 的价值是重排而不是凭空编。
2. **评价标准是"被追问时站得住"**，不是"好看"。这让"结论句当标题"成为可验证的产品主张，而不是审美偏好。
3. **改稿频率极高**。讲之前一定会改，所以"改"必须是一等公民，而不是生成完就结束。

## 2. 三条主张，以及为它们付出的代价

### 主张一：每页标题是一句可以被反驳的判断

坏标题「项目背景」，好标题「真正的瓶颈不在模型，在检索召回」。

代价：模型输出质量方差变大。名词标签怎么写都不会错，判断句会写歪。缓解办法是提示词里放**坏例子 / 好例子对照**，并且告诉模型「标题 ≤22 字，不要句号」。仍然会有失手的页，所以画布上每个字都能直接改——产品用可编辑性兜住模型的方差。

### 主张二：生成一次，排版无限次

骨架确认后，换版式、换主题、调顺序、改文字全是纯前端重算。这不只是体验设计，也是额度设计：一次生成约 2–4 CU，让用户在排版上反复试而不花钱，才敢让他"随便换着看"。

代价：版式必须是**数据驱动**的，不能是贴图模板。这就是 `layout.js` 存在的原因——10 种版式的每一种都是代码算出来的坐标，而不是设计师画的板子。

### 主张三：导出的 .pptx 还能改

文本框、形状、原生图表。评审可以双击图表改数据，这说明文件是真的。

代价：放弃了很多视觉效果（渐变、阴影、图片叠加），因为 PptxGenJS 对它们的支持不稳，而"导出后错位"比"不够炫"严重得多。宁可克制。

## 3. 为什么是 10 种版式、3 套主题

模板库的商业模式是"给你 200 套挑"，结果是每一套都不够合身。这里反过来：**版式是结构，主题是皮肤**。

- 版式对应"这段内容在讲什么关系"：并列（要点）、对立（对比）、先后（流程）、量级（数字）、
  证据（图表）、**多维度比较（表格）**、**一页一句（图文）**、**路径导航（目录）**。
- 主题只换颜色和字体，不换结构，所以任意组合都成立。

3 套主题（墨蓝 / 纸白 / 蓝图）覆盖了投影、打印、中性三种场合。再多就是选择负担。

## 4. 额度预算

| 动作 | 调用 | 估算 |
|---|---|---|
| 生成整份（8–10 页） | 1 次，输入约 1.5k token，输出 2–3k | 2–4 CU |
| 改单页 | 1 次，约 0.6k token | <1 CU |
| 换版式 / 换主题 / 改字 / 导出 | 0 次 | 0 |

开发期用 `anna-app dev --no-llm` 跑 UI，只在验证完整链路时花真额度；每次真实调用把 `_meta.quotaConsumed` 记下来（界面右下角有累计显示），不靠拍脑袋估。

## 5. 砍掉的东西

| 砍掉 | 理由 |
|---|---|
| AI 生图 | 一张几十 CU，且这类汇报里配图通常是噪音。想要就自己去 PowerPoint 加 |
| .docx / .pdf 解析 | 需要 mammoth / pdf.js 进 bundle（+500KB）且解析质量不稳。v1 用"粘贴"覆盖 80% 的场景 |
| 演讲备注 | 对"讲得清"有真实价值，但会显著拉长输出 token，挤占额度。放 v1.1 |
| 完整撤销栈 | 只做了页级操作。真要做撤销，状态模型要改成不可变 + 命令栈，一天不够 |
| 模板库 / 团队协作 / 主题编辑器 | 都不是这次要证明的东西 |
| 真图片版式 | 「图文」先只做文字视觉块：图片要上传管线 + `addImage`，且会把 bundle 和 256KB 的 state 上限都拖进来。收益不如先把表格和目录做扎实 |

## 6. 如果再多三天

1. **演讲备注**：每页一句话"这页你要说什么"，导出到 PPTX 的 notes。
2. **材料引用**：点一条 detail 能看到它来自材料的哪一段，降低"AI 编的"这种不信任。
3. **骨架视图**：现在改标题要逐页点，应该有一个"只看标题"的列表视图，一次性改完再排版。
4. **撤销**：改成 `history[]` + 命令模式，支持 ⌘Z。

前两个是用户价值，后两个是把"能改"做得更顺。
